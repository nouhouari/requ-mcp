Fixed on 2026-07-10 (PO green light, was previously blocked "pending PO/architect decision"): US-185 (admin manages `ScopeRestriction`), US-186 (silent masking of restricted content), US-187 (associate/remove restriction on an article), in `GEODIS-INTRANET/intranet-portal-api`. Root cause for most failures was "never built" (no `status` field, no delete guard, no members endpoint, no M:N), not code bugs. Full e2e proof lives in `test/news-rbac.e2e-spec.ts` describe block `'US-185/186/187 — ScopeRestriction (correctif P21)'` (18 AC-tagged tests, all green) plus the pre-existing `'P23 — ...'` block (403→404 assertion updated in place).

**Two deliberate reversals of the original P23/ADR-019 design — both intentional, not oversights:**

1. **403 → 404 on `GET /news/:slug` for a restricted article.** The original P23 code threw `CategoryAccessRestrictedException` (403) on direct access, explicitly documented as "an assumed deviation from ADR-019, never validated by security-reviewer." The Prisma schema comment on `CmsArticle.restrictionId` already said the *intended* design was 404 (silent masking) — the code just never matched its own doc comment. AC-1 of US-186 requires 404. Reversed to 404 with the PO's explicit go-ahead this session. If a future request wants the 403 back, that's a real product/security conversation, not a silent revert.

2. **Added an M:N junction table (`CmsArticleScopeRestriction`) alongside the legacy 1:1 `CmsArticle.restrictionId` FK**, even though the original migration comment for that FK said "Option C retenue — FK directe 1:1 ... pas de M:N natif" as a deliberate ADR-019 decision. US-187 AC-5 explicitly requires multiple simultaneous restrictions per article with AND semantics (member of ALL groups) — that migration comment itself pre-approved this exact evolution ("Évolution vers M:N possible plus tard sans casser cette colonne"), so this wasn't overriding the ADR, just executing its anticipated next step. The legacy FK column still works unmodified for backward compat; both mechanisms feed the same access-check (`ScopeRestrictionService.canAccessRestrictionSet`).

**Known scope cuts (documented as deliberate, not forgotten):**
- `GET /news/admin` (`ArticleAdminApiView.restrictionId`/`restrictionName`) still only reflects the *legacy single* restriction, not the full M:N set — no AC required the admin list view to expose the array, so it wasn't built. If a future story needs "show all restrictions in the admin list," that's new scope, not a bug.
- `DELETE /news/:id/restrictions/:restrictionId` (US-187 AC-2) returns **404** if the association didn't exist (not idempotent 204) — a deliberate REST-semantics choice since the AC didn't specify either way.
- Deleting a `ScopeRestriction` now requires it to be `INACTIVE` first (US-185 AC-5 guard) — `PATCH {status: INACTIVE}` before `DELETE`. Fail-open (`ON DELETE SET NULL`/`CASCADE`) is still the underlying DB behavior once that gate is passed.

See also [[intranet-portal-api-fake-prisma-e2e-convention]] for why every e2e spec's fake Prisma needed a new `cmsArticleScopeRestriction` table added, and [[project-stack-mismatch-intranet-portal-api]] for the NestJS-not-Spring context.

**HIGH security-reviewer finding fixed same day (2026-07-10), same session's M:N feature above — root cause: the M:N junction exclusion was never wired into the "no actor" code path.** `CmsArticleService.findPublished`/`findForMyNews`, when called WITHOUT an actor (the only three real no-actor callers: `HomeService.getHomepage`, `PersonalizedHomeService.loadMyNews`, `NewRecruitsService.findLatest` — all three go through `GET /home`), used to build a hardcoded `{ bypass: false, accessibleIds: [], blockedIds: [] }` literal. `accessibleIds: []` correctly fail-closed the *legacy* 1:1 `restrictionId` column, but `blockedIds: []` made `resolveBlockedArticleIds` believe there were zero blocking restrictions, short-circuiting *before ever querying* `CmsArticleScopeRestriction`. Net effect: an article restricted **only** via the new M:N junction (`POST /news/:id/restrictions`, legacy `restrictionId` column left `NULL` — the natural way to use the feature) rendered in plain text on Home/MyNews/NewRecruits for any authenticated user. `SearchService.searchNews` (both the tsvector and ILIKE-fallback paths) had the exact same gap but worse — it never referenced the junction table at all, not even a stub.

Fix: added `ScopeRestrictionService.resolveAnonymousVisibility()` (blockedIds = ALL currently-ACTIVE restriction ids, since with no actor no LDAP membership can ever be proven) and `resolveBlockedArticleIds(blockedIds)` (factored out, now shared by both `CmsArticleService` and the newly-injected `ScopeRestrictionService` in `SearchService`/`SearchModule`). Both call-sites in `CmsArticleService` now call `resolveAnonymousVisibility()` instead of the hardcoded literal.

**Test-infra fallout worth knowing before touching this area again:** wiring the real `ScopeRestrictionService` into the no-actor path means it now unconditionally queries `prisma.scopeRestriction`/`prisma.cmsArticleScopeRestriction` on every `GET /home`, `GET /home/new-recruits`, and `GET /search` request — even in e2e specs that never cared about restrictions before. 7 previously-green e2e spec files had **no fake table at all** for those two models and started 500ing: `home-rbac`, `home-admin-p10`, `stats-rbac`, `home-people-moments`, `search-rbac`, `social-rbac`, `personalization-rbac` (all under `test/*.e2e-spec.ts`) — each needed an empty `scopeRestriction`/`cmsArticleScopeRestriction` stub added to its own hand-rolled fake Prisma. Real e2e regression proof (not just unit) for the exploit was added to `home-rbac.e2e-spec.ts` (describe block `'GET /home — faille M:N sans acteur'`) and `search-rbac.e2e-spec.ts` (describe block `'news — faille M:N sans acteur'`) — both required building an *isolated* `app2`/`moduleRef` per test rather than reusing the file's shared `app`, because `ScopeRestrictionService.getTable()` memoizes for 5 minutes in-process and the shared app's cache was already populated (empty) by earlier tests in the same file before the restriction fixture existed. `home-rbac.e2e-spec.ts`'s generic `matchWhere` fake-Prisma helper also had a latent bug conflating `undefined` (no constraint) with literal `null` (must equal null) on `{ restrictionId: null }`-style clauses — silently made that whole clause a no-op; fixed alongside (needed `restrictionId: null` added as an explicit default field on its `ArticleRow`/`makeArticleRow` fixture type, since rows had no value there before → `undefined`, not `null`). `home-people-moments.e2e-spec.ts` (covers `NewRecruitsService` / `GET /home/new-recruits`) was left WITHOUT a dedicated e2e regression proof — its fake `cmsArticle.findMany` only inspects `where.status`/`where.category` and ignores `where.AND` entirely, so it can't exercise this filter at all without a bigger rewrite; the fix is still proven correct there at the unit level since `NewRecruitsService` calls the identical `CmsArticleService.findPublished` already covered in `cms-article.service.spec.ts`.
